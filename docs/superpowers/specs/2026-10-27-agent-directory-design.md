# AI agents in SuedeAI.directory — design for approval

Prepared October 27, 2026. Status: proposed; no product implementation authorized by this document. Baseline inspected: suede-creator-skills main `25641db0d42a58eec791dba61e6480694682b140`.

**Decision and approaches.** The user's latest choice, “actually do the full,” selects repository-based **and hosted agents**. Repository-only intake would reuse pinned-source review most directly but omit hosted products. A benchmark-first directory would delay launch until execution environments, accounts and budgets exist. The selected approach launches useful mixed profiles with evidence-specific ratings, then adds measured results when separately authorized. This supersedes the earlier repository-only choice.

**Scope.** Add an Agents section alongside Skills. List identifiable, runnable agent products/configurations with an official product or repository source, a documented access route, and stated license or service terms. Framework-only repositories, models, MCP servers, skill packs and unavailable products are not initial agent listings. Eligibility follows reviewed licensing, privacy and listing policy; numerical ratings do not gate admission. Public-source availability and deployment are separate fields: local, self-hosted or hosted software may have different licenses. Each product has one stable profile with explicitly named editions; assessments belong to an edition/configuration, never automatically to all editions. Builders choose the small presentation details within the existing design system.

**Ratings.** No overall agent score or skill-grade badge at launch. Show Documentation, applicable evidence ratings, and Performance/security evidence. Repository evidence applies wherever the reviewed edition has public source; Hosted disclosures applies to every hosted edition. A hosted edition can receive both, but source evidence must identify its relationship to the service, with deployed-revision equivalence marked unknown unless proven. All numeric ratings measure the stated evidence coverage, not correctness, safety or effectiveness. Display methodology and assessment date next to each rating.

| Rating | Ten binary checks; one point each |
| --- | --- |
| Documentation /10, common to both | Intended tasks; boundaries; access/setup instructions; prerequisites; model/provider requirements; worked example with expected outcome; tool/integration list; permission description; failure/recovery guidance; support or issue route |
| Repository evidence /10, repository edition | License text; attribution/notice information; immutable reviewed commit; documented distribution/source relationship; dependency manifest; resolved dependency inventory or lockfile; test files; CI definition invoking checks; release/change history; security reporting policy |
| Hosted disclosures /10, hosted edition | Service terms; dated pricing/usage-unit explanation; retention policy; model-training/data-use policy; authentication controls; permission/approval controls; audit/export documentation; deletion/revocation instructions; public service-status or incident information; product change history |

Each awarded point requires a checked criterion plus a citation with a path/section locator. Criteria use explicit item-specific completeness rules published in the methodology; keywords or file existence alone do not establish substantive documentation. A reviewer records an absent criterion as 0 only after inspecting the defined sources. Unreviewed or inaccessible evidence is `unknown`; incomplete assessments have a null score and show reviewed-check coverage, not a misleading partial total. A hosted-only edition has repository rating `not_applicable`; missing evidence is never silently treated as a tested failure. These are separate scales: do not combine or compare repository and hosted scores. Stars, sponsorships, commercial relationships and self-reported benchmark percentages contribute no points.

Capability, reliability, latency and cost are `not_tested` with null values unless a scoped test report exists. Future measured results require suite/version, tasks and acceptance checks, repetitions/denominator, all outcomes including failures, artifacts, model/version/configuration, permissions, environment, date and evaluator. Publisher or third-party results remain attributed evidence and do not become “Suede tested.” Security starts `not_assessed`; documented controls and static scans cannot establish runtime safety. Preserve findings, original severities, incomplete coverage and dispositions separately; no generic “safe” or “certified” badge.

**Catalog and evidence.** Add `directory/agents.json`, `directory/agents.schema.json`, versioned rubric data under `directory/agents/`, and reviewed receipts under `directory/agents/evidence/`. Product fields: stable ID/slug, name, publisher, official URLs, task tags, concise sourced description, edition records, review status. Edition fields: ID, deployment, source availability, license/terms URL, access documentation, model requirements, permission/cost disclosures, evidence IDs and typed assessments. Every receipt records evidence type (publisher documentation/source inspection/third-party result/Suede test), URL, locator, observation timestamp, reviewer, content SHA-256, edition/configuration and assessment scope. Preserve provenance; a hash alone does not prove origin.

Repository evidence binds the canonical repository, exact 40-character commit and relevant file digests verified at that commit; source links are immutable. Hosted evidence binds the official URL, observation time and section locator to a durable JSON record of short necessary excerpts and reviewed factual observations committed under `directory/agents/evidence/`. Hash these persisted records; do not claim to preserve or hash-verify complete hosted pages. These records survive local cleanup and are auditable through Git history. A later reviewer can reproduce our rating calculation and inspect cited observations, but must re-fetch for current publisher claims; historical full-page verification is unavailable unless an immutable publisher source exists. Record service version as `not_disclosed` when unavailable, never invent a source commit. No record fingerprints the deployed service. Refresh is manual and read-only in v1. Recheck after 30 days or known material changes; render old evidence as dated/stale without removing history or listings. A failed refresh preserves the last accepted snapshot and reports failure; it cannot create new scores. Builds validate retained records without network requests.

**Pages, search and submissions.** Preserve the existing Skills home, skill URLs and `/ai-agents-llm/` category. Add a visible Skills/Agents switch and generate `/agents/`, `/agents/<slug>/`, `/agents/methodology/`, `/agents/submit/`, `/agents/search-index.json` and `/agents/<slug>/report.json`. Profiles show editions, practical setup/access facts, scored checklists, cited claims and explicit untested states. Search returns one row per reviewed edition, labeled with product and edition and linked to its profile anchor. Counts distinguish products from editions. Search includes task, deployment, license/source availability and evidence status; default order is product then edition name. All ratings on a result belong to that edition. Documentation sorting spans editions; repository/hosted rating sorts restrict results to editions where that rating applies. Unknown scores sort after assessed ones; no averaging or strongest-edition selection. Use existing search styling and URL-state patterns with a separate agent index/client module, preserving skill search and shortlist behavior.

Add an agent-specific GitHub issue form linked from the agent submission page: add/recheck/correct/remove, official URL, optional repository, exact edition/scope and supporting evidence. Repository intake records a reviewed commit; hosted intake reviews official product/terms/privacy documentation. Claims are manually reviewed before admission. Give publishers a correction route without implying endorsement or contacting them automatically.

**Build and report integrity.** Add an agent renderer module invoked by `scripts/build-directory.mjs` and register every generated file in its existing `files` map before orphan cleanup. Reserve `agents` against repository-route collisions. Reuse the standalone builder's URL rewriting, sitemap and report hashing; give agent reports a schema version and kind discriminator. Reports contain catalog snapshot digest, evidence digests, rubric version, per-check reasons, edition scope and independent runtime/security states. Validate references and recompute scores from checks. Keep the current canonical serialization/hash convention and report-version marker so standalone host rewriting recalculates report identities correctly. Emit self-canonical public pages, breadcrumbs, CollectionPage/ItemList and appropriate SoftwareApplication/source metadata; omit fabricated aggregateRating, review counts and prices. Update llms.txt with separate agent/skill counts.

## Approved expansion: ungraded discovery

The user requested a large ungraded catalog alongside assessed listings on
2026-10-27. Add `/agents/ungraded/`, reachable from the Agents hub, with compact
static cards, search, task/deployment/source filters, URL state, live counts and
no-JS fallback. Each product has official source links and a visible check date.
Support multiple documented deployment options per product without duplicating
its editions. Public repository availability is not an open-source-license claim.
Do not grant numeric ratings, verification badges or security endorsements.
Keep ungraded data and search separate from assessed editions and skill scores.
Admission is limited to usable agents; exclude frameworks/models/servers/packs
alone. Source-backed counts must follow the actual accepted records. The same
signed draft PR holds the expansion, with no merge or deployment authorization.
